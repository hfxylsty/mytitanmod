# 10 · 内容清单（泰坦 / 召唤物 / 物品 / 方块）

## 本文件职责

本文回答一个问题：**这个模组最终要有哪些内容，第一个里程碑要做其中的哪一部分。**

它只做"点名与分档"，不做数值平衡，也不定义实现方式：

| 本文负责 | 本文不负责（由谁负责） |
|---|---|
| 泰坦分档、每条泰坦的定位与破防条件 | 泰坦 AI / 属性 / 网络同步的实现 → [02-architecture.md](02-architecture.md)、[03-gameplay-systems.md](03-gameplay-systems.md) |
| 召唤物五级谱系的内容结构 | 渲染与动画方案 → [04-client-rendering.md](04-client-rendering.md) |
| 物品 / 方块 / 材料的最小集与分档 | 目录约定与资源规范 → [05-data-and-assets.md](05-data-and-assets.md) |
| 数据驱动层需要哪些 JSON（清单级） | 里程碑排期与验收标准 → [06-roadmap.md](06-roadmap.md) |
| 命名纪律与原创性约束 | 合规裁定的最终口径 → [07-compliance.md](07-compliance.md) |

**数值约定**：本文出现的所有倍率、半径、时长、数量、上限**均为设计值，待平衡**；标「待验证」的条目表示写法或可行性尚未确认，不得当作既成事实写进代码。表格中若整列都是设计值，标记直接写在列名里。

**玩法事实来源**：MC百科资料页 <https://www.mcmod.cn/class/628.html>（仅提取玩法机制层面的事实，不提取任何具体名称与文本表达）。工程与合规边界依据 [00-overview.md](00-overview.md) 与 [PORT-PLAN.md](PORT-PLAN.md)。

## 一、命名纪律（先读这一节）

本文列出的**每一个中文名、英文名、注册 id 都是原创提案**。落地前必须过 [07-compliance.md](07-compliance.md) 的检查。

### 1.1 硬规则

| 规则 | 说明 |
|---|---|
| 禁止等同 | 不得与原模组的任何物品名、贴图名、音效名、模型名、语言文件条目**字面相同**，包括其官方中文译名 |
| 禁止近似到可混淆 | 不采用"改一个字"式命名（同音字、近义字替换）；必须是**重新构词** |
| 英文 id 自建 | 注册名一律用我们自己的词根，禁止照搬原模组的注册名结构 |
| 文本自建 | 语言文件、进度描述、提示语、成就文本全部自己撰写，禁止翻译或改写原模组文本 |
| 素材自建 | 贴图 / 模型 / 音效全部自建或使用明确授权的素材（见 05、07） |

### 1.2 功能位映射（只记功能，不复述原模组专名）

为避免"同一个功能位换个名字还是撞名"，我们把原模组的功能位与我们的原创命名**一对一固定**下来。本文档**不复述**原模组的具体专名——显式禁用名清单由 [07-compliance.md](07-compliance.md) 维护；在 07 补齐前，任何命名提案都不得直接提交到代码。

## 二、泰坦清单

### 2.1 规模决策：我们做几个

原模组发行版登记 19 种泰坦 BOSS + 61 种对应强化原版生物。**我们不做对等复刻**（[00-overview.md](00-overview.md) 第四节非目标第一条）。理由有两条，且都是工程性的：

1. 那是原团队 6 人多年的量，单人/单 agent 做到内容对等是 6~12 个月量级；
2. 我们的存在理由是**机制差异化**（五级召唤物 / 重生长 / 破防 / 双模式 / 伤害规则），泰坦数量少不影响这五条跑通，数量多反而会摊薄它们。

因此本文的规模定档为 **1 + 4 + 5 = 10 只**：

| 档位 | 数量 | 作用 | 判据 |
|---|---|---|---|
| **M1 首个泰坦** | **1** | 垂直切片，跑通"实体 → 渲染 → 破防 → 重生长 → 掉落"整条链路 | 能端到端验收，而不是内容量 |
| **M2 核心泰坦** | **4** | 覆盖 4 种不同的**破防条件原型**与 4 条不同的**召唤物谱系**，让系统显得"是系统"而不是特例 | 每只都必须带来一种新的破防机制 |
| **M3 扩展泰坦** | **5** | 后续可选，主要是题材铺量 | 不影响 M1/M2 的任何设计 |

### 2.2 字段说明

- **体型倍率**：相对原型生物渲染尺寸与碰撞箱的倍数。**M1 的僵尸泰坦按原版设定固定为 16×（32 格 × 16 格）**；
  其余泰坦的倍率仍是「设计值，待平衡」，可参考 16× 作为量级基准。
- **破防条件**：未破防时泰坦免疫绝大部分伤害；满足条件后进入**破防窗口**，窗口内才吃正常伤害。窗口结束后恢复减伤。
- **招牌技能**：该泰坦区别于同档其它泰坦的 1~2 个标志性行为，不含通用近战。
- **优先级**：P0 = M1 必做；P1/P2 = M2 分两批；P3/P4 = M3。

### 2.3 M1 · 首个泰坦（1 只）

|---|---|---|---|---|---|---|---|---|
| 僵尸泰坦 | Zombie Titan | `titan_zombie` | 僵尸 `minecraft:zombie` | **32 格高 × 16 格宽（16×）** | **碎甲**：胸前 3 片「腐骨甲片」为独立可攻击部位，全部击碎后进入 **8 秒**破防窗口；**30 秒**后甲片重生 | 巨剑横扫；腐疫践踏（地面 AoE，附带中毒）；召出忠诚者 | 普通 / 困难 | **P0** |

**外观设定（**来自原版描述，已核实并作为硬性设计约束**）**：

- 一只**手持巨型铁剑**、被**放大 16 倍**并高清化的僵尸
- **高 32 格、宽 16 格**

各特征的实现分工见 [31-art-spec-titan-zombie.md](31-art-spec-titan-zombie.md)：

> **命名与体型的修正记录（2026-10-03）**：本文档早期版本给这只泰坦自拟了
> 「Rotten Colossus / 腐骸泰坦」这个名字，并把体型写成「8.0×（设计值）」——
> 两者都**没有依据**，当时既没有原版资料也没核对英文名。
>
> 经用户提供原版外观描述后更正为：
> - 名称：**僵尸泰坦 / Zombie Titan**，注册 id `titan_zombie`
> - 体型：**32 格高 × 16 格宽（16×）**，碰撞箱 `sized(16.0F, 32.0F)`
> - 外观：手持巨型铁剑、周身橙黄粒子、四肢有关节、躯体分三节、低血亮绿透明护甲
>
> 保留「腐骨甲片」作为破防部位名（我方自拟，不与任何原作名重合）。

**为什么 M1 选它**：

1. **原型最简**——僵尸是原版 AI 最干净的近战怪，泰坦化后不需要额外写寻路或飞行逻辑，能把工时集中在真正难的地方（多部件、缩放、破防）。
2. **一次验证整条最难的链路**——它同时需要多部件实体（甲片）、`PartEntity` 级伤害判定、破防状态机、重生长、掉落表、召唤祭坛，正好覆盖 [PORT-PLAN.md](PORT-PLAN.md) 第五节列的垂直切片验证点。
3. **破防机制可复用**——"击碎 N 个部位 → 开窗口 → 部位重生"是最通用的破防模板，M2 的 3 只泰坦里有 2 只能直接复用它的实现，只是把"甲片"换成"关节""卵囊"。
4. **它是原版最经典的泰坦**——僵尸泰坦的辨识度最高，作为第一个可玩泰坦的展示价值最大。

**M1 只做这一只泰坦本体**，不顺便把 M2 的实体一起注册进去——垂直切片的价值在于"少而完整"。

## 三、召唤物谱系清单

### 3.1 结构：通用五级模板 + 泰坦专属变体

**不为每只泰坦各写五种召唤物。** 10 只泰坦 × 5 级 = 50 个实体，那是先把自己拖死。采用的是两层结构：

- **第一层：通用五级模板（5 个实体）**——五级各只有**一个**实体类，AI、职责、上限全部写在模板里，表现层按泰坦"换装"（贴图、粒子、伤害类型、增益）。
- **第二层：泰坦专属变体（每只泰坦 0~2 个）**——只有当某只泰坦的破防机制**必须**依赖一个特殊仆从时才新建实体；否则一律复用模板。

这样 M2 结束时的召唤物实体总数是 **5 个模板 + 最多 4 个变体 = 9 个**，而玩家看到的是"每只泰坦都有自己的教会"。

> 合规说明：五级的**职责划分**（治疗者 / 强化者 / 审判者 / 飞行先驱）属于玩法机制，可以借鉴；但**长袍配色、造型、文本、音效必须自建**，不得沿用原模组的紫 / 青 / 绿 / 红长袍视觉设定。中文称谓为通用宗教等级词，英文注册名一律自建（见 3.2 表），避免与原模组注册名撞名。

### 3.2 通用五级模板（列内数值均为「设计值，待平衡」）

| 级 | 中文称谓 | 我们的英文 id | 定位 | AI 要点 | 生成上限（设计值） | 是否每只泰坦都有 |
|---|---|---|---|---|---|---|
| 1 | 忠诚者 | `devotee` | 近战蜂群 | 攻击对应泰坦的攻击目标；仇恨跟随泰坦；不主动打无关生物 | **24** | 是 |
| 2 | 牧师 | `chaplain` | 治疗者 | 周期治疗附近友军（含泰坦本体，治疗量设上限）；自身低伤害 | **12** | 是 |
| 3 | 狂热者 | `zealot` | 强化突击 | 加速 / 高跳 / 闪避 / 额外减伤；可击杀体型大于自己的目标 | **8** | 是 |

上限的乘积效应需要实测：24+12+8+4+2 = 50 个仆从如果同时存在，对 TPS 的压力很大，因此**上限是每只泰坦独立计算**还是**全服共享**，留待 [03](03-gameplay-systems.md) 决定。

### 3.3 三个具体例子

**例 1 · 僵尸泰坦（M1）——只用模板，不做变体。**
M1 只注册 `devotee` 一个召唤物实体，通过数据（贴图 + 伤害类型 + 生成参数）绑定给僵尸泰坦，显示为"泰坦忠诚者"。圣骑士、主教在这一档**只留接口不实现**。这样垂直切片的实体数量保持最小，而"泰坦会造小弟"这条玩家可感知的体验已经成立。

**例 2 · 烬焰泰坦（M2）——主教替换为专属变体。**
通用主教偏"召唤 + 灼印"，而烬焰泰坦的破防条件是**熄核**，它需要一个能持续给泰坦"续火"的仆从，否则玩家熄灭外壳后泰坦自己就恢复不了。因此新增变体 `emberforge_hierarch`：它不召唤低阶仆从，而是**周期为泰坦外壳重新点火**，迫使玩家先处理它。这是一个"变体不为好看、而为机制服务"的典型：专属变体存在的唯一理由是**它的存在改变了破防流程**。

**例 3 · 终界泰坦（M2）——圣骑士替换为专属变体，且与破防条件耦合。**
终界泰坦的破防是"射落 6 枚浮游终界水晶"。通用圣骑士负责"先驱 + 送还残响"，而终界圣骑士额外承担**补晶**：当水晶被射落 3 枚以上时，它会尝试重新凝聚水晶（可被打断）。于是战斗形成三层节奏——玩家射水晶、圣骑士补水晶、泰坦本体输出；玩家必须先切掉圣骑士才能稳定推进破防。这是把 3.1 的两层结构真正用起来的样子。

> 结论：**通用模板保证规模可控，专属变体保证机制有辨识度。** 判断是否新建变体的唯一标准是"复用模板会不会让这只泰坦的破防条件失效"。

## 八、待验证与待决策

**待验证（写法 / 可行性未确认）**

1. 1.21.1 数据目录的单复数与精确路径（`recipe` / `loot_table` / `tags/item` 等），以 05 号文档为准。
2. **多部件巨型实体在 1.21.1 的可用做法**——原版 `EnderDragonPart` 机制能否支撑"甲片 / 关节 / 卵囊"这类独立可攻击部位，还是需要自建。**这一条直接决定 2.3~2.5 的破防条件能不能照写**，必须优先验证。
3. 1.21.1 附魔 JSON 的 schema（`supported_items`、`effects` 等字段）。
4. NeoForge 21.1 通用标签前缀（`c:`）的确切写法。
5. 召唤物上限（24/12/8/4/2）在真实场景下对 TPS 的影响；上限是每泰坦独立还是全服共享。

**待决策**

1. **五级中文称谓的合规口径**：中文"忠诚者 / 牧师 / 狂热者 / 主教 / 圣骑士"是通用宗教等级词，但它们与原模组官方译名的组合方式一致。本文已把**英文注册名全部改为自建词根**（`devotee` / `chaplain` / `zealot` / `hierarch` / `paladin`），中文显示名是否保留，**需 [07-compliance.md](07-compliance.md) 裁定**。这是本文最大的合规不确定点。
2. 长袍 / 配色 / 造型的具体方案——必须自建，不得沿用原模组的紫 / 青 / 绿 / 红分工，但"颜色即职责"的设计思路可以保留。
3. 泰坦掉落是否统一含「泰坦残响」，还是每只泰坦只掉专属材料。
4. 召唤祭坛是否需要自定义配方类型（`recipe_type`），还是仅用方块逻辑。
5. 是否做自定义维度，以及第三个模式是否进 M3。
6. 噩梦模式相对普通模式的完整差异表（伤害上限、重生长概率、仆从上限是否同步调整），由 [03-gameplay-systems.md](03-gameplay-systems.md) 定稿后回填到 [2.6](#26-泰坦通用参数神性规则)。
