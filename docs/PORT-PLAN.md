# 泰坦模组迁移 1.21.1 — 方案分析

> 日期：2026-10-03　状态：**方案分析阶段（未开始编码）**
> 依据：`E:\titanmod\.tmp\titans-src\`（已下载的真实源码）、`E:\titanmod\.tmp\mac-src\`、mcmod 资料页

## 〇、结论先行

**不要做"代码迁移"，要做"玩法重实现"。**

理由不是"迁移很难"，而是三条硬事实叠加后，迁移这条路在经济上不成立：

1. **仓库里是骨架，不是完整模组**——发行版内容量是仓库代码的 8~10 倍，而那部分内容不存在于任何公开源码里；
2. **两个前置仓库都没有 LICENSE**——照抄代码再发布，法律上站不住；
3. **资源层（模型/贴图/音效）无法随代码一起迁移**——1.12.2 的模型格式与 1.21.1 不兼容，等于要重做。

而"玩法"本身不受版权保护。做净室重实现，可以同时绕开这三个问题，并且第一个可玩版本会来得快得多。

## 三、四个真实的拦路虎

### 拦路虎 1：仓库是骨架，发行版内容不在里面

- 仓库实体注册表只有 **10 个实体**：7 个泰坦原型（蠹虫/洞穴蜘蛛/蜘蛛/骷髅/僵尸/尸壳/僵尸猪人）+ 凋灵斯拉 + 2 个闪电实体。
- mcmod 登记的发行版内容是：**19 种泰坦 BOSS + 61 种强化原版生物 = 80 个**，另有 85 实体 / 222 物品方块 / 7 附魔 / 3 效果 / 2 群系 / 2 维度。
- 也就是说，**公开源码覆盖不到发行版的 1/8**。真正的 0.495(1.7.10) / 0.5(1.12.2) 内容只存在于分发出去的 jar 里。

→ 想"完整复刻发行版"，唯一途径是反编译 jar。这既涉及法律问题，工程量也远超重写。

### 拦路虎 2：Mixin 配置指向不存在的类

`META-INF/thetitans_mixin.json` 声明了：
- `MixinNetHandlerPlayServer`（通用）
- `MixinEntityRenderer`（客户端）

但这两个类在 Titans 仓库里**一个都不存在**，它们来自 MrbtUtil 的 `net.mrbt0907.util.mixin.injection` 包（shadowJar 会把包名 relocate 过去）。
加上 `thetitans_at.cfg` 里 25 条 **SRG 名**的 Access Transformer，大量直改原版内部：

```
public-f net.minecraft.entity.EntityLivingBase func_110143_aJ()F   # getHealth
public-f net.minecraft.item.ItemSword field_150933_b
public    net.minecraft.client.renderer.EntityRenderer field_78530_s
public    net.minecraft.entity.projectile.EntityArrow *
```

这些是**对原版内部实现的强耦合**。1.21.1 里这些字段/方法要么改了名（Mojang 官方映射）、要么整个类被重构（`EntityRenderer` 已拆解）、要么机制换成数据驱动。每一条都要单独重新设计。

### 拦路虎 3：资源层无法迁移

| 资源 | 数量 | 能否直接用 |
|---|---|---|
| 贴图 png | 777 | △ 素材版权归原作者，且需按 1.21.1 规范整理 |
| 模型 json | 485 | **✗** 1.12.2 模型格式与 1.21.1 不同（`item/generated` 已废弃，改用 `item/handheld` + `items/` 定义） |
| blockstate json | 252 | △ 命名空间从 `blocks/` 改为 `block/` |
| 音效 ogg | 270 | △ 需重建 `sounds.json` |
| 语言文件 | 2（含中文） | ✓ 格式可用（`.lang` → `.json`） |
| **data/（配方/战利品/标签）** | **0** | **✗ 完全没有**，1.21.1 必须补齐 |

注意最后一行：仓库里**根本没有 `data/` 目录**。1.12.2 时代配方写在 Java 代码里，而 1.21.1 要求数据驱动 JSON。这部分等于从零做。

### 拦路虎 4：团队自己的技能边界

已装的 `minecraft-modding` 技能 v0.1 里，**没有移植文件**（`05-porting.md` 未创建），而且这几个文件全部是"P2 排期待创建"：

| 需要的能力 | 技能状态 |
|---|---|
| 内容型（方块/物品/配方/标签/战利品） | ✅ 已交付 |
| 机器/容器/能量/流体 | ❌ 未创建 |
| 世界生成 | ❌ 未创建 |
| **实体** | ❌ **未创建** |
| **客户端（GUI/渲染/粒子）** | ❌ **未创建** |
| **网络（多人同步/自定义包）** | ❌ **未创建** |
| 移植与版本差异 | ❌ 未创建 |

而泰坦模组的核心恰恰是**实体 + 渲染 + 网络**——落在三个未覆盖区。所以第一步不该是移植，而是先补这块能力（我们自己趟一遍就能沉淀成技能文档，反过来喂给技能）。

生态里还有：
- [The Titans: Old Dream (Unofficial)](https://www.mcmod.cn/class/27006.html) —— 1.20.1 的非官方移植（CurseForge）
- [新泰坦生物：撼世之物 (Neo Titans Mod)](https://www.mcmod.cn/class/20584.html) —— 另一个中文圈的新泰坦项目

**这对我们意味着什么：**

1. **正面**：证明"1.12.2 → 现代版本重实现"这条路技术上完全可行，而且有人已经跑通了。它自称的做法（优化动画、平衡数值、去掉创造模式特判）恰好印证了我上面推荐的净室重实现路线。
2. **负面（要认真对待）**：如果目标是"在 1.21.x 上玩到泰坦"，那么**已经有一个 93 万下载、持续维护的成品**，而且它在 1.21.4 而不是 1.21.1。我们从头做一个，短期内不可能比它更完整。
3. **因此需要重新明确目的**，三选一：
   - **(a) 只是想玩** → 直接装 Neo The Titans（1.21.4）成本最低，不用开发。缺点：1.21.4 不是 1.21.1，且它 All Rights Reserved、无源码，不能改。
   - **(b) 想自己动手学/做** → 按本方案做净室重实现，目标是"我自己的泰坦模组"，不跟它比内容量。
   - **(c) 想做出差异化** → 需要先想清楚我们做什么它没做：例如还原**原版的召唤物谱系**（忠诚者/牧师/狂热者/主教/圣骑士五级体系）、**重生长机制**、**噩梦/灭神模式**、**维度战**——从它的清单看，这些原版特色机制它似乎没重点做。这反而是我们的机会。

**我的建议**：如果是 (a)，别开发；如果是 (b)/(c)，继续走净室路线，但把"差异化"写进设计目标，否则做出来只是 Neo The Titans 的拙劣版本。

## 四、四条可选路线

| 路线 | 做法 | 优点 | 致命问题 | 建议 |
|---|---|---|---|---|
| **A. 净室重实现** | 只读 mcmod 玩法描述，从零写 1.21.1 代码，自己画/买素材 | 合法、可控、增量可玩、第一个版本快 | 达不到发行版内容量 | ✅ **推荐** |
| B. 迁移 1.12.2 仓库代码 | 把 144 个文件改写成 NeoForge | 有现成代码 | 只有骨架 + 无 LICENSE + 资源层重做 | ❌ |
| C. 反编译发行版 jar | 反编译 0.5/0.495 再移植 | 内容最全 | 法律风险最高、反编译产物质量差、工作量大 | ❌ |
| D. 基于 Neo The Titans 二次开发 | 用现成的 1.21.4 同类模组 | 起点高 | 需核实授权关系；且 1.21.4 ≠ 1.21.1 | ⚠️ 待核实 |

路线 A 的具体含义——把"玩法"当规格书，把"代码"完全重写：

- **可以借鉴**：玩法机制、数值设计、系统结构、界面流程（这些是"思想"，不受版权保护）
- **不能碰**：源码（含反编译产物）、贴图、音效、模型、语言文件的具体文本表达
- **自建**：多部件巨型实体、伤害/减伤规则、召唤物体系、泰坦生成规则、重生长机制

## 五、建议的垂直切片（第一步做什么）

**目标：1 个泰坦 + 1 个召唤物 + 自定义渲染 + 1 件武器，端到端跑通。**

选它是因为它能一次性验证整条最难的链路：

| 模块 | 验证点 |
|---|---|
| 实体 | `DeferredRegister` 注册、属性（`EntityAttributeCreationEvent`）、刷怪蛋 |
| 多部件巨型实体 | 1.12.2 的 `IEntityMultiPart`/`MultiPartEntityPart` → 1.21.1 的对应做法 |
| 缩放 | 5~20 倍体型的渲染与碰撞箱 |
| 客户端渲染 | `EntityRenderer` 注册、`EntityModel`/`ModelPart` 或第三方动画库 |
| 召唤物 | AI 目标继承、生成上限 |
| 网络 | 至少一个自定义 payload 验证同步 |
| 数据层 | 掉落表、配方、标签 JSON |
| 构建 | `gradlew build` + `runClient` 进游戏看到泰坦 |

**验收标准（可自动判定的部分）**：
1. `gradlew build` 输出 `BUILD SUCCESSFUL`；
2. `runClient` 进主菜单，日志无致命错误，且日志中出现我们的 mod 名；
3. 进世界后能用刷怪蛋生成泰坦，泰坦可见、会动、有碰撞；
4. 攻击泰坦 → 伤害被减伤规则处理（在日志/血量上可观测）；
5. `/summon` 指令可用我们的实体 id 生成。

**不做**：19 个泰坦、自定义维度、GUI、成就系统。切片只是验证链路。

## 六、工作量量级（粗估，需后续校准）

| 阶段 | 内容 | 量级 |
|---|---|---|
| 0. 技能补全 | 自己趟通实体/渲染/网络，写成参考文档 | 与阶段 1 重叠 |
| 1. 垂直切片 | 1 泰坦 + 召唤物 + 渲染 + 武器 | **2~4 周** |
| 2. 核心玩法 | 3~5 个泰坦、召唤物谱系、重生长、减伤规则、生成规则 | **1~2 个月** |
| 3. 内容扩展 | 物品/方块/装备/附魔/维度 | **3~6 个月** |
| 4. 打磨发布 | 平衡、多人测试、兼容性 | **1~2 个月** |

对照：发行版 19 泰坦 + 222 物品 + 2 维度，是原作者（团队 6 人）多年的量。单人/单 agent 做到"玩法对等"是 **6~12 个月**量级的项目，不适合当作第一个里程碑。

3. **美术来源**：泰坦贴图自己画、买素材、还是先用纯色占位跑通逻辑？建议**先占位**，美术后置。
